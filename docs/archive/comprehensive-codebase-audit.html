MediFlow Comprehensive Codebase Audit

Audit date: 2026-08-09 | Scope: backend, frontend, Docker, database, infrastructure, and documentation

Executive Summary

MediFlow is intended to be a patient-management platform for hospitals, clinics, and multi-provider care networks. Its planned shape is a Spring Boot microservice backend, React operations console, PostgreSQL per domain, Kafka events, service discovery, an API gateway, and cloud/container deployment.

The workspace is currently an early vertical slice plus architecture scaffolding rather than a production-ready platform.

  1. The backend has a compile-breaking auth identity mismatch: BaseEntity uses UUID while auth entities redeclare String IDs.
  2. The API gateway has no routes, so the intended frontend-to-backend path is not connected.
  3. The frontend is a static prototype with hard-coded patient data and no API or authentication integration.
  4. Lab, medical-record, and pharmacy services are present but omitted from the root Maven reactor.
  5. Database passwords, a fallback JWT secret, wildcard CORS, plaintext Kafka, and schema auto-update create security and operational risk.

1. Project Understanding and Architecture

MediFlow is designed to coordinate patient registration, records, appointments, doctors, billing, notifications, analytics, authentication, and future lab, pharmacy, and medical-record workflows.

Primary users

Clinical staffSearch patients, review context, and coordinate care.
Doctors and care teamsManage schedules, patient activity, and follow-up work.
AdministratorsRegister patients, manage providers, billing, and notifications.
Platform administratorsManage access, configuration, health, and reporting.

Entry points

  • Root Maven reactor: pom.xml
  • API gateway on port 8080: gateway configuration
  • Auth API on port 8081: AuthController
  • Domain APIs under /api/v1/..., including patient, doctor, appointment, billing, notification, and analytics controllers.
  • React/Vite console: App.tsx
  • Local PostgreSQL and Kafka: docker-compose.yml

3. Technical Debt, Bugs, and Risks

Correctness

  • Auth identity conflict: BaseEntity defines UUID identity, while User, Role, and RefreshToken redeclare String IDs.
  • Invalid dates return the wrong status: PatientService calls LocalDate.parse directly; malformed input can become a generic 500 instead of a structured 400.
  • Frontend actions are placeholders: PatientsPage renders hard-coded patients and non-functional Add patient actions.
  • OpenAPI is incomplete: docs/api/OpenAPI.yaml is only a skeletal document, so client/server contract drift is likely.

Security

  • Committed database credential defaults exist in docker-compose.yml and service YAML files.
  • Auth configuration falls back to change-me-in-production for JWT signing.
  • Gateway CORS allows every origin, method, and header.
  • Multiple services use Hibernate ddl-auto: update; production should use versioned migrations and validate.
  • Kafka is configured with plaintext listeners for local development only; production needs TLS/SASL and ACLs.
  • Domain authorization needs explicit role and ownership checks for patient and billing data.

Reliability and performance

  • Patient retrieval uses unbounded findAll(); add pagination, filters, and bounded responses.
  • No visible idempotency, retry, dead-letter, timeout, circuit-breaker, or backpressure policy exists.
  • No executable health checks, readiness probes, resource limits, backup policy, or database pool policy is visible.

5. Prioritized Three-Phase Action Plan

Phase 1: Quick Wins and Bug Fixes

  1. Fix UUID/String auth identity mismatch.
  2. Add request/date validation and consistent error responses.
  3. Apply Spring Boot packaging and verify runnable jars.
  4. Define the supported service set and quarantine unfinished modules.
  5. Add .env.example; remove insecure production defaults.
  6. Replace ddl-auto: update with Flyway migrations.
  7. Add gateway routes and smoke tests.
  8. Add Maven Wrapper, CI, and security scanning.
  9. Replace frontend dev Docker image with a production build.
  10. Document local startup, ports, seed data, and smoke tests.

Exit criteria: Root build and tests pass; Compose health checks pass; gateway routes auth and one domain flow; production profiles have no secret fallbacks.

Phase 2: Core Architecture and UI Refactoring

  1. Define service ownership, data boundaries, and versioned contracts.
  2. Complete OpenAPI and generate typed frontend clients.
  3. Add URL routing, route guards, session handling, loading, and error states.
  4. Add pagination, filters, sorting, and validation to core workflows.
  5. Add authorization tests and Testcontainers integration coverage.
  6. Add structured logs, metrics, traces, request IDs, and readiness probes.
  7. Create a service template and shared build convention.

Exit criteria: A staff user can authenticate and complete a patient-to-appointment workflow through the gateway with integration coverage and useful telemetry.

Phase 3: High-Impact Feature Expansion

  1. Implement outbox-backed Kafka workflows.
  2. Add patient identity matching, consent, tenant boundaries, and FHIR-aligned adapters.
  3. Add search/read models and performance caching.
  4. Add operational analytics for access, throughput, no-shows, wait times, and billing.
  5. Add governed AI assistance with human approval and PHI controls.
  6. Complete lab, medical-record, and pharmacy domains only after contracts and operational ownership are defined.
  7. Harden deployment with immutable images, secret references, autoscaling, backups, disaster recovery, and progressive delivery.

Exit criteria: Core workflows meet documented SLOs; events are traceable and replay-safe; interoperability is contract-tested; automation and AI have explicit safety controls.
